# Email and notification verification, 2 October 2026

Ordinary bookings created unpaid now publish their existing deterministic paid-booking confirmation when payment becomes confirmed, provided the booking is still in a valid booking state. Replayed transitions and subsequent updates do not create another logical email. Gifts, Business, Health+ and cancelled deliveries retain their existing handling. The existing delivery-updated Eventarc route is reused; no native change is required.

`resend-delivery-events.js` is a separate, fail-closed signed webhook receiver. It verifies exact raw bytes with Svix and requires `RESEND_WEBHOOK_SECRET`. It records only provider IDs, event type and event time; no recipient addresses, message bodies or raw provider payloads are persisted. `emailQueue.status` continues to mean send processing, while `providerDeliveryStatus` records delivery/bounce/failure independently. Duplicate webhook IDs do not create repeated alerts and older events cannot replace a newer provider outcome. A matching receipt not yet present returns a retryable response rather than silently dropping the outcome. It sends no emails and never changes marketing consent or customer billing.

Activation must use one Resend webhook, with delivered/delayed/bounced/complained/failed/suppressed/sent events, the `/resend/events` route, and its signing secret in Secret Manager. Keep the existing transactional-email consumer private and keep its send-only Resend key restricted. Do not mark provider integration complete until a valid signed event reaches this receiver and forged input fails. Failure structured log event: `transactional_email_delivery_failure`.

The emulator-only `qa-email-lifecycle.cjs` refuses to run without `FIRESTORE_EMULATOR_HOST`. It creates isolated Gifts payment-ledger/source fixtures, drives approval, curation, ready, delivery and Story, checks queue/in-app duplicate protection and consumes messages through a stub provider that accepts only `example.test` recipients. It does not call Stripe, FCM or Resend. Fixture cleanup must show no root/subcollections. This is source integration evidence, not authenticated deployed event delivery or device/inbox certification.

On 2 October the existing three Gifts notification Eventarc queues were zero and recent notification-service requests returned 200. Earlier CPU quota 503s remain historical reliability evidence, not proof of a current failed queue. Capacity changes must preserve existing owners and coordinate with backend recovery. No historical resends or native/store artifacts are included.
